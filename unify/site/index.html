The sensor axis is data, not architecture — switch engines and watch it change while the weights stay identical.

One weight set, three sensor counts

FD001 exposes 15 sensors, FD003 16, FD002 and FD004 21. A conventional model needs one instance per layout, because the input width is baked into the first layer. Here the sensor axis is a dynamic ONNX dimension and each channel carries a learned sensor-ID embedding, so the same weights accept all three. Switch engines above — the shape readout changes, the model does not reload.

Different widths

Input is (1, S, 30) with S free. The encoder is shared across channels; cross-attention pools them into a fixed vector, so S never reaches a fixed-width layer.

Different time units

C-MAPSS counts cycles, FEMTO seconds, XJTU minutes. The model predicts a fraction of life in [0,1], denormalised per dataset by life_scale — 125 for C-MAPSS. Without that, the dataset with the biggest numbers would dominate the loss.

Different operating conditions

FD002 and FD004 run at six conditions whose sensor effect is larger than the degradation signal. Inputs here are z-scored per condition with the shipped training statistics — the same lookup the Pi does.

What is actually happening when you press Run

1 · Window

The last 30 cycles of the engine are sliced and transposed to (1, S, 30).

2 · Normalise

Already z-scored at build time with the training statistics, per operating condition. Recomputing them from the live series would normalise away the degradation trend.

3 · Infer

onnxruntime-web runs the 190 KB graph on WASM and returns rul and attn. Timed with performance.now().

4 · Denormalise

Output is clamped to [0,1] and multiplied by 125 to get cycles — exactly what edge/inference.py does.

Build step: python scripts/build_demo_site.py. It exports the engines and asserts that the tensors this page receives reproduce the Python predictor's answer to within 0.002 cycles — so if the browser and the Pi ever disagree, the build fails first.

What this demo does not prove

latency

The millisecond figure above is your browser on WASM, not the Pi. The measured Pi 5 number is 0.423 ms p50 at 4 threads. An x86 laptop is not an ARM proxy, and a WASM runtime is not a native one — the two numbers are not comparable.

datasets

Every engine here is C-MAPSS. FEMTO and XJTU-SY are not downloaded, so "any dataset" is demonstrated across four subsets and three sensor layouts, not across three physically different machines.

accuracy

A RandomForest baseline on 105 engineered features gets 14.41 RMSE against this model's 14.51. That is a tie, not a win. The case for this architecture is the 190 KB footprint and the dynamic sensor axis you are watching — not accuracy.

the live rig

The motor rig has no ground-truth RUL — you cannot run a bearing to destruction in a semester. Its MPU-6050 also tops out at 1 kHz against the bearing datasets' 25.6 kHz. The rig demonstrates the pipeline; the accuracy comes from datasets.

Why these engines can be scored at all: they are held-out official test units, and the split is by engine, never by window — two windows from one engine overlap by 29 of 30 cycles, so a window-level split leaks almost perfectly. Guarded by test_split_is_by_unit_not_by_window.

Run the whole stack yourself

No downloads. Generated run-to-failure data, about five minutes.

$ pip install -r requirements-train.txt
$ make smoke      # build · train · export · test
